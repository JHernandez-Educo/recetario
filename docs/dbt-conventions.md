# dbt Conventions — House Style Mapped onto dbt

- Date: 2026-09-29
- Purpose: reconcile Julio's ETL skill suite (raw-to-clean-etl, clean-to-dimension-etl,
  clean-to-fact-etl, sql-formatting-standards) with dbt Core best practices.
  Rule of thumb: **dbt owns the mechanics, the house style owns the SQL.**

## 1. What dbt replaces (boilerplate we stop writing)

| House skill pattern | dbt equivalent | Notes |
|---|---|---|
| 5-step delete-insert template (Steps 1, 2, 5) | `materialized='incremental'`, `incremental_strategy='delete+insert'`, `unique_key=[...]` | The *entire* #to_process / DELETE / INSERT scaffolding is generated by the adapter. Same semantics, zero hand-written plumbing — and it's the same "never MERGE" philosophy the skills mandate |
| `#to_process` temp table + PK CLUSTERED | dbt-internal temp relations | Gone entirely |
| Hand-written `CREATE TABLE` DDL + typing phase | dbt generates DDL from the model's SELECT | Types come from explicit CASTs in the model (house rule "explicit CAST, no TRY_CAST" carries over 1:1) |
| `UX_{schema}_{table}_bk` unique index | `data_tests: unique` / `dbt_utils.unique_combination_of_columns` on the business key | Same intent (1 row per key), enforced as a build-failing test instead of an index. DuckDB local doesn't benefit from index tuning |
| Column Parity Check (Phase 3) | `schema.yml` column list + tests; `dbt ls`/docs diffing | Declared once, checked every build |
| `nnd_created` / `nnd_updated` metadata | dlt's `_dlt_load_id` + our `captured_at` | dlt already stamps lineage; no GETDATE() defaults needed |
| `WITH (NOLOCK)` | n/a | SQL Server–ism; nothing to port |
| `{{ range_start_point }}` templating | `{{ this }}` + `is_incremental()` filters | dbt's native incremental predicates. NOTE: the "which rows are new" filter is still written BY US inside the model — dbt does not auto-detect it |
| ROW_NUMBER dedup on every clean build | Usually unnecessary here | dlt's merge write-disposition already dedupes raw products to one row per key; price_events is append-only unique by grain. Dedup chain applies only on genuine grain mismatch |

## 2. What stays exactly as the house style (applies inside every model)

From `sql-formatting-standards`, unchanged:

- **Leading commas**, never trailing
- **Tabs**, not spaces
- **`WHERE 1=1`** first condition, `AND`s on new lines
- **Single-line `ROW_NUMBER()`**: `ROW_NUMBER() OVER(PARTITION BY ... ORDER BY ... DESC) AS rnk`
- **CTE names `rnkd` → `deduped` → `cleaned`** — used ONLY when the source truly has more
  rows per key than the target grain (dbt's delete+insert does NOT dedupe within a batch;
  `unique_key` is delete-matching, not a constraint). In this stack dlt's merge already
  guarantees one row per key in `raw_*.products`, and `price_events` is unique by
  construction — so most clean models need NO dedup chain. Latest-event *selection*
  (current price per SKU) is a different job that uses the same window function, in marts
- **Never MERGE** (delete+insert strategy is the house rule, now as one config line)
- **Never TRY_CAST/TRY_CONVERT** — explicit CAST only, fail loudly
- Naming: `price_events_FACT`, `ingredients_DIM`, `recipe_lines_BRIDGE` (lowercase body,
  ALL-CAPS role suffix); `{entity}_id_PK` / `{entity}_id_FK`; `is_{description}` flags
- Step-comment banners welcome inside longer models for readability

## 2b. Duplicates policy (house rule)

Duplicates are resolved ONLY at the raw → clean boundary. From the clean schemas onward a duplicate
is a defect, never data: **every clean and marts model carries a build-failing uniqueness
test on its declared grain.** Nothing downstream of clean ever silently dedupes — it fails
loudly instead. "Clean means clean by definition."

## 3. Layer → dbt config mapping

| Layer | Location | Schema | Materialization |
|---|---|---|---|
| raw | dlt-owned (`raw_vtex`, `raw_shopify`) | declared as dbt **sources** in `models/sources.yml`; dbt never writes here | n/a |
| clean, per source | `models/clean_vtex/`, `models/clean_shopify/` | `clean_vtex`, `clean_shopify` | `table` (or `incremental` delete+insert on the natural key once volume warrants) |
| marts | `models/marts/` | `marts` | `table`; serving views as `view` |

`generate_schema_name` macro is overridden so configured schemas are used verbatim
(`clean_vtex`, not `main_clean_vtex`).

## 4. dbt best practices adopted (the "learn dbt properly" list)

1. One model per file. dbt needs unique file names, so per-source clean models are prefixed and aliased: `vtex_price_events.sql` builds `clean_vtex.price_events`. Marts keep filename = table name (`price_events_FACT.sql`). The union of sources happens in the marts.
2. `source()` and `ref()` only — no hard-coded table names, ever. This is what draws the lineage graph.
3. Every folder gets a `schema.yml`: description per model and column (feeds dbt docs), tests beside descriptions.
4. Tests as the quality gate: `unique`/`not_null` on business keys, `accepted_values`,
   range tests for sanity (e.g., `net_grams` between 1 and 50,000 — catches the
   "50 g vs 10 tons of flour" absurdities), and the x100 price assertion
   (`price_check_ok = false` count must be 0) as a build-failing test.
5. `dbt docs generate` is the documentation surface; descriptions live in YAML next to the code.
6. Portable SQL; anything DuckDB-specific quarantined and commented.

## 5. Tooling

- **dbt MCP** (official, dbt Labs): configured in `.mcp.json`, CLI-only mode
  (`DBT_PROJECT_DIR` + `DBT_PATH`); gives run/test/build/docs + project metadata from chat.
- Later: `dagster-dbt` folds every model into the same asset graph as the connectors.

## 6. Verdict on writing dbt versions of the house skills

Defer. This document + the first few models ARE the template. Once ~3–4 models exist and
the pattern is stable, a `dbt-model-generator` skill (house style + delete+insert +
rnkd/deduped/cleaned + schema.yml scaffold) becomes worth writing — from working examples,
not speculation.
